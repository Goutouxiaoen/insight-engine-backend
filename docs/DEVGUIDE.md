# 第一部分：核心理念

在写代码前，先建立三条铁律。这三条直接决定你后面会不会"做不下去"。

## 铁律 1：文件是唯一的记忆，对话不是

**CodeBuddy 的对话上下文是易失的、有上限的，但文件是持久的、可被反复读取的。**

所以一切"进度、决策、待办、约定"都必须**落盘成文件**，而不是只存在于对话里。任何时候你新开一个对话，只要让工具去读那几个"真相源文件"，它就能在 30 秒内重建完整上下文。

> 类比：对话上下文 = 短期记忆（工作记忆）；文件 = 长期记忆（硬盘）。你要做的，就是**把短期记忆随时沉淀到硬盘**。

## 铁律 2：一个对话只做一件事，做完就关闭

**不要让一个对话"从建项目一路写到上线"。** 那样上下文必然爆掉，且越到后面 AI 越容易"忘记"前面的约定。

正确做法：**按"阶段 → 里程碑 → 任务"三级切分，每个对话只负责一个任务**，任务完成、代码提交、更新真相源文件后，就结束这个对话，开新对话继续。

## 铁律 3：先定"真相源"，再写代码

在动手前，先确定 5 份**真相源文件（Source of Truth）**，它们是你和 AI 之间的"共享大脑"。后面每阶段、每个对话都围绕它们展开。

真相源文件清单（详见附录 A）：

| 文件 | 作用 | 谁维护 |
|------|------|--------|
| `docs/PRD.md` | 产品做什么（已产出） | 你 + 工具 |
| `docs/TD.md` | 技术怎么做（已产出） | 你 + 工具 |
| `docs/IF.md` | 接口契约（已产出） | 你 + 工具 |
| `docs/DEVGUIDE.md` | 本文档（协作方法） | 你 + 工具 |
| `docs/PROGRESS.md` | **进度与状态追踪（核心！）** | 你 + 工具 |

> 其中 `PROGRESS.md` 是最关键的动态文件，后面会详细讲它的结构。

# 第二部分：单文件真相源策略（解决记忆丢失的根本办法）

## 2.1 为什么需要 PROGRESS.md

你担心的"多轮对话后记忆丢失"，根本原因是没有一个**跨对话、跨会话的持久状态**。解决办法不是"让 AI 记得更久"，而是**让 AI 每次都能从一个固定文件里读到最新状态**。

`PROGRESS.md` 就是这个固定文件。它的内容永远反映项目当前真实状态：

- 哪些模块做完了、哪些在做、哪些没开始
- 每个模块的关键决策、踩过的坑
- 当前阻塞的问题
- 下一步要做什么

## 2.3 真相源文件的维护规则

1. **每次对话结束前**，最后一步一定是：更新 `PROGRESS.md` 的状态。
2. **每次对话开始时**，第一步一定是：让工具读取 `PROGRESS.md` + 相关文档。
3. **重大决策/踩坑**立即记入对应小节，不要拖到对话结束。
4. 文档文件命名固定、路径固定，**永不改名、永不移动**。

# 第三部分：开发顺序与阶段规划

## 3.1 为什么顺序重要

中大型项目的开发顺序必须遵循**依赖拓扑排序**：先做被依赖的底层，再做依赖它的上层。否则会出现"上层写好了但下层接口还没定"的返工。

## 3.2 推荐开发顺序（12 个阶段）

按 TD 的工程结构，推荐以下顺序。**每个阶段是一个独立对话批次**。

```
阶段 0：环境准备（一次性）
  ├── 安装 JDK17 / Maven / Docker / Node
  └── 初始化 Git 仓库 + .gitignore

阶段 1：工程骨架
  ├── 父 POM + BOM（insight-engine-dependencies）
  ├── common 公共模块
  ├── starter-web（统一响应/异常/TraceID）
  └── 验证：mvn 能编译通过

阶段 2：基础设施层
  ├── docker-compose（postgres/pgvector、redis、rabbitmq、nacos、minio）
  ├── init.sql（DDL + seed 数据）
  └── 验证：docker compose up 后各中间件健康

阶段 3：认证与用户（UMS 服务）★第一个完整微服务
  ├── 登录/注册/刷新/登出
  ├── JWT + Spring Security
  ├── RBAC（角色/权限）
  └── Knife4j 接入（接口文档可用）

阶段 4：网关（gateway）
  ├── 路由配置
  ├── JWT 全局过滤器
  ├── 统一跨域、限流
  └── 验证：通过网关访问 UMS 接口

阶段 5：工作空间与组织
  ├── workspace 服务
  ├── 数据权限拦截器
  └── 成员管理

阶段 6：模型网关（model 服务）★核心 AI 能力
  ├── 厂商/模型/路由
  ├── ChatAdapter 适配器抽象 + 通义/Ollama 实现
  ├── 流式 SSE + 用量计量
  └── 验证：能真实调用通义返回结果

阶段 7：知识库（kb 服务）
  ├── 文档上传 + MinIO
  ├── RabbitMQ 异步解析 + 切片 + Embedding
  ├── PGVector 检索 + 重排 + 溯源
  └── 验证：上传 PDF → 检索命中

阶段 8：工具市场（tool 服务）
  ├── 内置工具 + HTTP 工具
  ├── 工具调试
  └── 验证：HTTP 工具可调用

阶段 9：Agent（agent 服务）★核心 AI 能力
  ├── Agent CRUD + 版本
  ├── ReAct + Function Calling
  ├── 关联知识库 + 工具
  └── 验证：Agent 完成"知识检索+工具调用"闭环

阶段 10：对话（conv 服务）
  ├── 会话 + 消息 + 流式
  ├── 反馈
  └── 验证：前端能流式对话

阶段 11：计费 + 监控（billing + obs）
  ├── 配额 + 用量 + 账单导出
  ├── Micrometer 指标 + 审计日志
  └── 验证：账单能导出

阶段 12：前端 + 部署收尾
  ├── admin 管理端（工具主导）
  ├── chat 对话端（工具主导）
  ├── docker-compose 全量编排
  └── 验证：一键启动，端到端演示
```

## 3.3 为什么"模型网关"和"Agent"是核心

- **模型网关**：是整个平台的"发动机"，其他模块都依赖它。做扎实了，后面 RAG/Agent 都水到渠成。
- **Agent**：是简历上最亮眼的部分（ReAct + Function Calling + RAG 闭环），也是面试必问。
- 这两个模块建议**分配最多时间和精力**，并写出高质量设计笔记（写进 PROGRESS 的决策记录）。

# 第四部分：如何组织对话（解决上下文超限与进度同步）

这是你三个困惑的核心答案。

## 4.1 三个困惑的本质

| 你的困惑 | 本质 | 解法 |
|----------|------|------|
| 一个任务对话走到黑 → 上下文超出 | 任务粒度过大，对话承载过多 | 任务拆细，一对话一任务 |
| 多轮对话后记忆丢失 | 状态只存在对话里，没落盘 | 真相源文件策略 |
| 多开对话，进度记忆难同步 | 多个对话各写各的，没有统一状态 | 单一 PROGRESS.md + 串行化 |

## 4.2 核心原则：串行开发，而非并行开多个对话

**重要结论：不要同时开多个对话并行开发不同模块。**

原因：
1. 多个对话会**同时写 PROGRESS.md**，产生冲突（互相覆盖）
2. AI 之间看不到彼此对话的内容，进度必然错乱
3. 你作为唯一开发者，串行开发更符合实际，也更容易掌控

**正确做法**：
- 一次只开一个"开发对话"
- 这个对话做完一个任务 → 更新 PROGRESS → 关闭
- 再开下一个对话做下一个任务

## 4.3 对话的三种类型

把你的对话分为三类，每类用途清晰：

| 类型 | 用途 | 生命周期 | 是否更新真相源 |
|------|------|----------|----------------|
| **开发对话** | 写代码、实现功能 | 一个任务，做完关闭 | 是（必须） |
| **学习对话** | 问技术问题、学技能 | 问完即弃，可长期挂着 | 否 |
| **Review 对话** | 审查代码、找 bug | 一次审查，看完关闭 | 是（记录问题） |

**关键规则**：
- **开发对话**严格"一任务一对话"
- **学习对话**可以随便聊，不用担心上下文，因为它不写代码
- **Review 对话**独立于开发对话，避免"既当运动员又当裁判"

## 4.4 标准对话开场白（模板）

每次新开一个开发对话，用这个开场白，让 AI 快速进入状态：

```
我正在开发"智擎 AI"项目（企业级 AI Agent 编排平台）。

请先阅读以下文件，建立完整上下文：
1. d:/CodexProject/docs/PRD.md（产品需求）
2. d:/CodexProject/docs/TD.md（技术方案）
3. d:/CodexProject/docs/IF.md（接口设计）
4. d:/CodexProject/docs/PROGRESS.md（当前进度）

读完后，请先用 5 行以内的话复述：我们现在做到哪了、下一步要做什么。

然后，我们开始今天的任务：【XXX 具体任务】
```

> 这段开场白的价值：让 AI **先读文件再干活**，而不是凭对话里的零散信息猜测。AI 复述进度，你也能顺便确认它读对了。

## 4.5 防止上下文超限的实操技巧

1. **任务粒度**：一个任务的代码量控制在 **3~8 个文件、500~1500 行**以内。超过就拆。
2. **及时收尾**：任务完成立刻让 AI 更新 PROGRESS 并总结，不要继续闲聊。
3. **不用一条对话问两个大方向的问题**：比如"顺便把前端也写了"，这会撑爆上下文。
4. **善用"读文件"而非"贴代码"**：让 AI 去读代码文件，而不是你在对话里粘贴大段代码。
5. **上下文快满时的信号**：AI 开始重复说之前说过的话、忘记你前面的约束、答非所问 → 立即结束对话，开新对话并用开场白重建。

# 第五部分：每阶段的标准协作套路

## 5.1 一个阶段的标准流程（循环）

```
1. 【开新对话】用开场白模板 + 声明本阶段任务
2. 【AI 读真相源】读 PRD/TD/IF/PROGRESS
3. 【AI 复述】确认理解无误
4. 【定验收标准】双方对齐本任务的"完成"定义（做什么、不做什么）
5. 【写代码】AI 生成代码 + 你本地运行验证
6. 【跑通验证】编译/启动/冒烟测试（见全栈 skill 的 Step 4）
7. 【更新真相源】AI 更新 PROGRESS.md（状态、决策、踩坑）
8. 【收尾总结】AI 输出：本次做了什么、怎么跑、遗留问题
9. 【关对话】开下一任务对话
```

## 5.2 每个任务的验收四件套

源自全栈开发 skill 的 Step 4，落到本项目：

1. **编译通过**：`mvn clean package -DskipTests`
2. **启动成功**：服务能起来，Nacos 注册成功
3. **接口冒烟**：`curl` 或 Knife4j 调通关键接口
4. **数据落库**：关键操作能查到数据

**没有跑通这四件套，任务不算完成。**

## 5.3 推荐的"开发 + Review 分离"节奏

```
开发对话（写代码）
    ↓ 提交 git commit
Review 对话（读代码、查业务逻辑、找 bug）
    ↓ 记录问题到 PROGRESS「待解决问题」
回到开发对话或新对话修复
```

> 强烈建议：**每完成一个里程碑，开一个独立的 Review 对话**，让 AI 以"代码审查者"身份审视刚写的代码。这能帮你"及时 review 业务逻辑实现"（详见第七部分）。

# 第六部分：及时学习后端技能的方法

你的目标是"及时学习以上提到的后端开发技能"。这里给出**学用结合**的具体方法。

## 6.1 原则：在项目中"用到即学"，而非"先学完再做"

不要试图先把所有技术学完再动手，那样永远学不完。正确方式是：

**每做一个模块，就顺带深入学该模块用到的技术。**

## 6.2 每个模块对应的"学习任务"

| 开发模块 | 顺带学习的技能 | 学习方式 |
|----------|---------------|----------|
| 工程骨架 | Maven 多模块、依赖管理 | 让 AI 讲解 POM 结构 |
| UMS | Spring Security、JWT、RBAC | 让 AI 逐行讲解 Security 配置 |
| gateway | Spring Cloud Gateway、过滤器链 | 让 AI 画调用时序图 |
| 工作空间 | MyBatis-Plus 拦截器、数据权限 | 让 AI 讲拦截器原理 |
| 模型网关 | Spring AI、适配器模式、SSE | 让 AI 讲抽象与流式实现 |
| 知识库 | PGVector、RabbitMQ、Embedding | 让 AI 讲 RAG 全链路 |
| 工具 | 反射、JSON Schema | 让 AI 讲 Function Calling 协议 |
| Agent | ReAct、LangChain4j | 让 AI 讲 ReAct 循环源码 |
| 对话 | WebFlux、SSE | 让 AI 讲响应式编程 |
| 计费 | EasyExcel、定时任务 | 让 AI 讲账单生成 |
| 监控 | Micrometer、Prometheus | 让 AI 讲指标埋点 |
| 部署 | Docker、Docker Compose | 让 AI 讲容器化 |

## 6.3 学习对话的提问模板

```
【学习模式】我想深入理解刚写的 XX 模块里的 YY 技术。

请基于我项目里的实际代码（路径：XXX），
1. 逐行解释这段代码做了什么、为什么这么写
2. 这里的设计模式是什么？为什么用这个模式？
3. 如果要面试，面试官会怎么追问这个点？我该怎么答？
4. 给我 3 个容易踩的坑和规避方法

请用"先讲原理，再结合我的代码"的方式回答。
```

## 6.4 建立个人技能笔记（建议）

每学完一个技术点，让 AI 帮你生成一段**可复习的笔记**，追加到 `docs/LEARNING.md`（学习笔记真相源）。这样到面试前，你有一份"自己项目里的技术点笔记"可快速复习。

```
docs/LEARNING.md 结构：
# 学习笔记
## JWT 认证
- 原理：...
- 我的项目里怎么用的：...
- 面试追问点：...
```

# 第七部分：如何让工具帮你 Review 业务逻辑

你要求"能及时 review 业务逻辑实现"。这是用 CodeBuddy 很有价值的能力。

## 7.1 Review 的三个层次

| 层次 | 审查内容 | 何时做 |
|------|----------|--------|
| L1 语法/编译 | 能不能编译、有没有明显 bug | 每个任务做完 |
| L2 逻辑正确性 | 业务逻辑对不对、边界情况 | 每个里程碑 |
| L3 架构质量 | 是否符合 TD 设计、有无坏味道 | 每个阶段 |

## 7.2 Review 对话的标准 Prompt

```
【Review 模式】请以资深 Java 架构师身份，审查我刚完成的 XX 模块。

代码路径：d:/CodexProject/insight-engine-modules/insight-engine-xxx/

请对照以下文档审查：
- 技术方案：d:/CodexProject/docs/TD.md
- 接口设计：d:/CodexProject/docs/IF.md

请重点检查：
1. 业务逻辑是否正确、完整（对照 PRD/IF）
2. 异常处理是否遗漏（空值、边界、并发）
3. 是否遵循 TD 的设计约定（分层、统一响应、TraceID）
```

## 7.3 Review 结果的处理

1. 让 AI 把 Review 结论写入 PROGRESS「待解决问题」或「踩坑记录」
2. 你筛选后，开新的开发对话逐条修复
3. 修复完再 Review 一次，形成闭环

# 第八部分：前端协作策略（你只需初步了解）

你明确说"前端多数由工具开发，我只是初步了解"。这没问题，但要把握几个关键点，避免前端成为黑洞。

## 8.1 前端开发的定位

- **前端不写业务逻辑**，只做"界面 + 调用后端接口"
- 后端接口已由 IF.md 定义清楚，前端严格照接口实现
- 前端先行？不，**后端先行**，前端在阶段 12 才做

## 8.2 前端开发时你只需把握三件事

1. **接口对齐**：前端调用的接口必须和 IF.md 一致（路径、字段、错误码）
2. **页面清单**：哪些页面、哪些功能，PRD 第 11 章已列
3. **验收标准**：页面能跑、能连后端、能流式对话

## 8.3 前端开发对话的标准 Prompt

```
【前端开发】请为"智擎 AI"开发管理端 XX 页面。

- 技术栈：Vue 3 + Vite + TypeScript + Arco Design + Pinia + Axios
- 接口契约：请读 d:/CodexProject/docs/IF.md 中的 XX 章节
- 页面要求：请读 d:/CodexProject/docs/PRD.md 第 11 章信息架构

请实现：
1. XX 页面的完整组件
2. 调用后端接口的 API 封装
3. 加载态/空态/错误态处理

前端我只需初步了解，请给出：关键代码 + 简短的"这一块为什么这么写"说明。
```

## 8.4 前端工程约定

- 前端代码放 `insight-engine-web/` 下
- admin 和 chat 两个独立工程
- API 封装统一放 `src/api/`，按模块分文件，对应 IF.md 章节
- 类型定义放 `src/types/`，对应后端 DTO


Commit 类型：`feat`（功能）/ `fix`（修复）/ `docs`（文档）/ `refactor`（重构）
