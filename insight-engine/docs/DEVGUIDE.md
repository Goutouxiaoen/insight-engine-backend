# 第零部分：30 秒快速上手（实操速查）

> 如果你只想快速知道"下一步具体怎么做"，看这一节就够。详细原理见后面各章节与附录 D。
>
> **所有可复制的 prompt 模板集中在「附录 B」（编号 P1~P16）**，正文与附录 D 只引用编号、不再重复粘贴。要复制模板，直接跳到附录 B。

## 现在就能做的 5 件事（按顺序）

1. **确认环境**：打开终端，运行下面命令，把结果告诉 AI
   ```bash
   java -version; mvn -v; docker --version; node -v
   ```
2. **开一个"环境准备"对话**：复制附录 B 的「P1 开场白」粘贴即可。
3. **AI 会先读 `docs/PROGRESS.md`** 重建上下文，然后引导你装环境。
4. **每完成一步**，让 AI 更新 `docs/PROGRESS.md` 并 `git commit`。
5. **每做完一个任务就关对话**，开新对话继续下一个任务。

## 记住这一句

> **新对话先读 PROGRESS，旧对话结束先写 PROGRESS。**

# 第一部分：核心理念

在写代码前，先建立三条铁律。这三条直接决定你后面会不会"做不下去"。

## 铁律 1：文件是唯一的记忆，对话不是

**CodeBuddy 的对话上下文是易失的、有上限的，但文件是持久的、可被反复读取的。**

所以一切"进度、决策、待办、约定"都必须**落盘成文件**，而不是只存在于对话里。任何时候你新开一个对话，只要让工具去读那几个"真相源文件"，它就能在 30 秒内重建完整上下文。

> 类比：对话上下文 = 短期记忆（工作记忆）；文件 = 长期记忆（硬盘）。你要做的，就是**把短期记忆随时沉淀到硬盘**。

## 铁律 2：一个对话只做一件事，做完就关闭

**不要让一个对话"从建项目一路写到上线"。** 那样上下文必然爆掉，且越到后面 AI 越容易"忘记"前面的约定。

正确做法：**按"阶段 → 里程碑 → 任务"三级切分，每个对话只负责一个任务**，任务完成、代码提交、更新真相源文件后，就结束这个对话，开新对话继续。

## 铁律 3：先定"真相源"，再写代码

在动手前，先确定 5 份**真相源文件（Source of Truth）**，它们是你和 AI 之间的"共享大脑"。后面每阶段、每个对话都围绕它们展开。

真相源文件清单（详见附录 A）：

| 文件 | 作用 | 谁维护 |
|------|------|--------|
| `docs/PRD.md` | 产品做什么（已产出） | 你 + 工具 |
| `docs/TD.md` | 技术怎么做（已产出） | 你 + 工具 |
| `docs/IF.md` | 接口契约（已产出） | 你 + 工具 |
| `docs/DEVGUIDE.md` | 本文档（协作方法） | 你 + 工具 |
| `docs/PROGRESS.md` | **进度与状态追踪（核心！）** | 你 + 工具 |

> 其中 `PROGRESS.md` 是最关键的动态文件，后面会详细讲它的结构。

# 第二部分：单文件真相源策略（解决记忆丢失的根本办法）

## 2.1 为什么需要 PROGRESS.md

你担心的"多轮对话后记忆丢失"，根本原因是没有一个**跨对话、跨会话的持久状态**。解决办法不是"让 AI 记得更久"，而是**让 AI 每次都能从一个固定文件里读到最新状态**。

`PROGRESS.md` 就是这个固定文件。它的内容永远反映项目当前真实状态：

- 哪些模块做完了、哪些在做、哪些没开始
- 每个模块的关键决策、踩过的坑
- 当前阻塞的问题
- 下一步要做什么

## 2.2 PROGRESS.md 的标准结构（建议直接照抄）

```markdown

## 2.3 真相源文件的维护规则

1. **每次对话结束前**，最后一步一定是：更新 `PROGRESS.md` 的状态。
2. **每次对话开始时**，第一步一定是：让工具读取 `PROGRESS.md` + 相关文档。
3. **重大决策/踩坑**立即记入对应小节，不要拖到对话结束。
4. 文档文件命名固定、路径固定，**永不改名、永不移动**。

# 第三部分：开发顺序与阶段规划

## 3.1 为什么顺序重要

中大型项目的开发顺序必须遵循**依赖拓扑排序**：先做被依赖的底层，再做依赖它的上层。否则会出现"上层写好了但下层接口还没定"的返工。

## 3.2 推荐开发顺序（12 个阶段）

按 TD 的工程结构，推荐以下顺序。**每个阶段是一个独立对话批次**。

```
阶段 0：环境准备（一次性）
  ├── 安装 JDK17 / Maven / Docker / Node
  └── 初始化 Git 仓库 + .gitignore

阶段 1：工程骨架
  ├── 父 POM + BOM（insight-engine-dependencies）
  ├── common 公共模块
  ├── starter-web（统一响应/异常/TraceID）
  └── 验证：mvn 能编译通过

阶段 2：基础设施层
  ├── docker-compose（postgres/pgvector、redis、rabbitmq、nacos、minio）
  ├── init.sql（DDL + seed 数据）
  └── 验证：docker compose up 后各中间件健康

阶段 3：认证与用户（UMS 服务）★第一个完整微服务
  ├── 登录/注册/刷新/登出
  ├── JWT + Spring Security
  ├── RBAC（角色/权限）
  └── Knife4j 接入（接口文档可用）

阶段 4：网关（gateway）
  ├── 路由配置
  ├── JWT 全局过滤器
  ├── 统一跨域、限流
  └── 验证：通过网关访问 UMS 接口

阶段 5：工作空间与组织
  ├── workspace 服务
  ├── 数据权限拦截器
  └── 成员管理

阶段 6：模型网关（model 服务）★核心 AI 能力
  ├── 厂商/模型/路由
  ├── ChatAdapter 适配器抽象 + 通义/Ollama 实现
  ├── 流式 SSE + 用量计量
  └── 验证：能真实调用通义返回结果

阶段 7：知识库（kb 服务）
  ├── 文档上传 + MinIO
  ├── RabbitMQ 异步解析 + 切片 + Embedding
  ├── PGVector 检索 + 重排 + 溯源
  └── 验证：上传 PDF → 检索命中

阶段 8：工具市场（tool 服务）
  ├── 内置工具 + HTTP 工具
  ├── 工具调试
  └── 验证：HTTP 工具可调用

阶段 9：Agent（agent 服务）★核心 AI 能力
  ├── Agent CRUD + 版本
  ├── ReAct + Function Calling
  ├── 关联知识库 + 工具
  └── 验证：Agent 完成"知识检索+工具调用"闭环

阶段 10：对话（conv 服务）
  ├── 会话 + 消息 + 流式
  ├── 反馈
  └── 验证：前端能流式对话

阶段 11：计费 + 监控（billing + obs）
  ├── 配额 + 用量 + 账单导出
  ├── Micrometer 指标 + 审计日志
  └── 验证：账单能导出

阶段 12：前端 + 部署收尾
  ├── admin 管理端（工具主导）
  ├── chat 对话端（工具主导）
  ├── docker-compose 全量编排
  └── 验证：一键启动，端到端演示
```

## 3.3 为什么"模型网关"和"Agent"是核心

- **模型网关**：是整个平台的"发动机"，其他模块都依赖它。做扎实了，后面 RAG/Agent 都水到渠成。
- **Agent**：是简历上最亮眼的部分（ReAct + Function Calling + RAG 闭环），也是面试必问。
- 这两个模块建议**分配最多时间和精力**，并写出高质量设计笔记（写进 PROGRESS 的决策记录）。

# 第四部分：如何组织对话（解决上下文超限与进度同步）

这是你三个困惑的核心答案。

## 4.1 三个困惑的本质

| 你的困惑 | 本质 | 解法 |
|----------|------|------|
| 一个任务对话走到黑 → 上下文超出 | 任务粒度过大，对话承载过多 | 任务拆细，一对话一任务 |
| 多轮对话后记忆丢失 | 状态只存在对话里，没落盘 | 真相源文件策略 |
| 多开对话，进度记忆难同步 | 多个对话各写各的，没有统一状态 | 单一 PROGRESS.md + 串行化 |

## 4.2 核心原则：串行开发，而非并行开多个对话

**重要结论：不要同时开多个对话并行开发不同模块。**

原因：
1. 多个对话会**同时写 PROGRESS.md**，产生冲突（互相覆盖）
2. AI 之间看不到彼此对话的内容，进度必然错乱
3. 你作为唯一开发者，串行开发更符合实际，也更容易掌控

**正确做法**：
- 一次只开一个"开发对话"
- 这个对话做完一个任务 → 更新 PROGRESS → 关闭
- 再开下一个对话做下一个任务

## 4.3 对话的三种类型

把你的对话分为三类，每类用途清晰：

| 类型 | 用途 | 生命周期 | 是否更新真相源 |
|------|------|----------|----------------|
| **开发对话** | 写代码、实现功能 | 一个任务，做完关闭 | 是（必须） |
| **学习对话** | 问技术问题、学技能 | 问完即弃，可长期挂着 | 否 |
| **Review 对话** | 审查代码、找 bug | 一次审查，看完关闭 | 是（记录问题） |

**关键规则**：
- **开发对话**严格"一任务一对话"
- **学习对话**可以随便聊，不用担心上下文，因为它不写代码
- **Review 对话**独立于开发对话，避免"既当运动员又当裁判"

## 4.4 标准对话开场白（模板）

每次新开一个开发对话，用「P1 开场白」（见附录 B）让 AI 快速进入状态，按需追加「P2 行为约束」「P3 代码质量约束」。

> 这段开场白的价值：让 AI **先读文件再干活**，而不是凭对话里的零散信息猜测。AI 复述进度，你也能顺便确认它读对了。

## 4.5 防止上下文超限的实操技巧

1. **任务粒度**：一个任务的代码量控制在 **3~8 个文件、500~1500 行**以内。超过就拆。
2. **及时收尾**：任务完成立刻让 AI 更新 PROGRESS 并总结，不要继续闲聊。
3. **不用一条对话问两个大方向的问题**：比如"顺便把前端也写了"，这会撑爆上下文。
4. **善用"读文件"而非"贴代码"**：让 AI 去读代码文件，而不是你在对话里粘贴大段代码。
5. **上下文快满时的信号**：AI 开始重复说之前说过的话、忘记你前面的约束、答非所问 → 立即结束对话，开新对话并用开场白重建。

# 第五部分：每阶段的标准协作套路

## 5.1 一个阶段的标准流程（循环）

```
1. 【开新对话】用开场白模板 + 声明本阶段任务
2. 【AI 读真相源】读 PRD/TD/IF/PROGRESS
3. 【AI 复述】确认理解无误
4. 【定验收标准】双方对齐本任务的"完成"定义（做什么、不做什么）
5. 【写代码】AI 生成代码 + 你本地运行验证
6. 【跑通验证】编译/启动/冒烟测试（见全栈 skill 的 Step 4）
7. 【更新真相源】AI 更新 PROGRESS.md（状态、决策、踩坑）
8. 【收尾总结】AI 输出：本次做了什么、怎么跑、遗留问题
9. 【关对话】开下一任务对话
```

## 5.2 每个任务的验收四件套

源自全栈开发 skill 的 Step 4，落到本项目：

1. **编译通过**：`mvn clean package -DskipTests`
2. **启动成功**：服务能起来，Nacos 注册成功
3. **接口冒烟**：`curl` 或 Knife4j 调通关键接口
4. **数据落库**：关键操作能查到数据

**没有跑通这四件套，任务不算完成。**

## 5.3 推荐的"开发 + Review 分离"节奏

```
开发对话（写代码）
    ↓ 提交 git commit
Review 对话（读代码、查业务逻辑、找 bug）
    ↓ 记录问题到 PROGRESS「待解决问题」
回到开发对话或新对话修复
```

> 强烈建议：**每完成一个里程碑，开一个独立的 Review 对话**，让 AI 以"代码审查者"身份审视刚写的代码。这能帮你"及时 review 业务逻辑实现"（详见第七部分）。

# 第五·五部分：给 AI 的强指令与约束（防止发散 / 乱改 / 破坏）

> 这是**防止 AI 跑偏、破坏已有成果**的实操指南。你在开发中遇到的最大风险，往往不是"AI 不会写"，而是"AI 太主动，改了不该改的东西"。
> 解决办法：**用强指令（硬约束）提前锁死 AI 的行为边界**。

## 5.5.1 为什么要给"强指令"

AI 有两个"天然倾向"需要主动压制：

1. **发散倾向**：你说做一个登录，它可能顺手"优化"了数据库、重构了配置、加了没要求的功能。
2. **过度修改倾向**：为了"看起来更完整"，它可能改掉你已经跑通的旧代码、改文档、改无关文件。

强指令的作用 = **把 AI 的"自由发挥空间"锁死在你要的范围内**。

## 5.5.2 万能约束模板（每次开发对话必加）

> 用「P2 行为约束」+「P3 代码质量约束」（见附录 B），粘在开场白后面。它是"最小改动 + 聚焦任务 + 不偷懒"的通用护栏。

## 5.5.3 按场景拆分的强指令

按需选用以下场景约束（全文见附录 B）：

| 场景 | 模板 |
|------|------|
| 只写新代码，不碰旧代码 | P10 |
| 修复 Bug，只改一处 | P11 |
| Review 只读不写 | P12 |
| 前端开发（约束最严） | P13 |
| 文档更新 | P14 |

## 5.5.4 三个最有效的"防发散"话术

当 AI 开始发散、要改无关东西时，用「P15 防发散话术」（见附录 B）中的任意一句打断。

## 5.5.5 关于"乱动已写好的代码"的兜底手段

即使给了强指令，AI 仍可能越界。用以下手段兜底：

1. **Git 是后悔药**：每个任务一个 commit，改坏了 `git checkout -- <file>` 即可回滚单个文件，`git reset --hard` 回滚整个任务。
2. **改前先看 diff**：让 AI 改完用 `git diff` 展示改动，你确认范围符合预期再 commit。
3. **Review 分离**：开发对话和 Review 对话分开，Review 对话专门查"有没有改不该改的"。
4. **锁文档**：`docs/` 下的文档改完后，除非明确要求，一律让 AI 不许碰。

## 5.5.6 关于"不动不该动的文档"

你的困惑"不要动不该改的文档"是高频痛点。明确规则：

- **PRD / TD / IF**：是"设计基线"，开发阶段原则上**冻结**。需求/设计变更时，先让你确认，再由你决定是否改。
- **PROGRESS.md**：是"动态状态"，**每次任务收尾才更新**，其余时候不碰。
- **LEARNING.md**：只在学习对话结束时追加。
- **DEVGUIDE.md**：只在协作方式调整时改。

> 一句话：**设计文档是"宪法"（稳定），进度文档是"日报"（常更新），别让 AI 搞反。**

## 5.5.7 代码质量约束（防止简化逻辑 / 不写注释 / 不守规范）

> 这是 AI 写代码最普遍的"偷懒"行为，必须用硬约束锁死。你提到三点（简略逻辑、不写注释、不守规范），下面补全为完整清单。

### 你提的三点 + 对应约束

| 你担心的 | 典型表现 | 硬约束 |
|----------|----------|--------|
| 简略/简化逻辑 | 把多分支合并成 `if-else` 一行、省略边界判断、用 TODO 搪塞 | 业务逻辑完整实现，禁止 TODO/占位符 |
| 不写注释 | 整个类无注释，或只写"废话注释" | 关键代码写中文注释，说明"为什么"而非"做了什么" |
| 不遵守企业级规范 | 分层混乱、异常裸抛、入参不校验、魔法数字 | 严格按 TD 分层 + 统一异常 + 参数校验 + 常量提取 |

### 我补充的 5 类"AI 爱偷懒"行为

1. **省略异常处理**：直接 `catch (Exception e) { e.printStackTrace(); }` 或吞掉异常。
   → 约束：不吞异常、不返回裸堆栈、错误码符合 IF 附录 A。

2. **不校验入参**：`@RequestParam String id` 直接拿来用，不判空、不判格式。
   → 约束：`@Valid`/JSR-303 完整校验，不信任客户端输入。

3. **写魔法数字/字符串**：`if (status == 1)`、`"admin"` 硬编码到处飞。
   → 约束：统一提取为常量/枚举。

4. **方法过长、职责混乱**：一个方法 200 行塞满所有逻辑。
   → 约束：单一职责，方法一般 ≤ 50 行。

5. **生成伪代码/空实现**：写 `// 这里后续实现` 或 `return null;` 占位。
   → 约束：不生成伪代码、空实现、占位方法。

### 质量约束速记（粘进开场白用）

> 用「P3 代码质量约束」（见附录 B），直接粘进开场白。

### 关于注释的特别说明（你最容易踩的坑）

AI 写注释有两种极端，都要纠正：

- **极端一：完全不写** → 约束"关键代码必须写注释"
- **极端二：写废话注释** → 如 `// 设置名字` 配 `setName()`，纯噪声

**正确注释标准**（让 AI 遵循）：

```
✅ 好的注释（写"为什么"）：
   // 网关下发明文 header，业务服务不重复解析 JWT，减少 secret 分发
✅ 好的注释（写"复杂逻辑意图"）：
   // 先向量召回 TopK*4，再应用层过滤 metadata，
   // 避免 PGVector 与 jsonb 组合选错索引
❌ 废话注释（不写）：
   // 获取用户
   User user = getUser();
```

# 第八部分：前端协作策略（你只需初步了解）

你明确说"前端多数由工具开发，我只是初步了解"。这没问题，但要把握几个关键点，避免前端成为黑洞。

## 8.1 前端开发的定位

- **前端不写业务逻辑**，只做"界面 + 调用后端接口"
- 后端接口已由 IF.md 定义清楚，前端严格照接口实现
- 前端先行？不，**后端先行**，前端在阶段 12 才做

## 8.2 前端开发时你只需把握三件事

1. **接口对齐**：前端调用的接口必须和 IF.md 一致（路径、字段、错误码）
2. **页面清单**：哪些页面、哪些功能，PRD 第 11 章已列
3. **验收标准**：页面能跑、能连后端、能流式对话

## 8.3 前端开发对话的标准 Prompt

用「P7 前端开发对话」+「P13 前端开发约束」（见附录 B）。

## 8.4 前端工程约定

- 前端代码放 `insight-engine-web/` 下
- admin 和 chat 两个独立工程
- API 封装统一放 `src/api/`，按模块分文件，对应 IF.md 章节
- 类型定义放 `src/types/`，对应后端 DTO

## 8.5 接口联调标准（前后端分离的核心约定）

> 这是前后端分离最容易扯皮的地方，必须先定死规则，避免"前端说字段对、后端说路径对、谁都不读谁"。

### 8.5.1 总原则：单一事实源 = IF.md

**前端和后端都只认 `docs/IF.md`，谁也不读谁的代码。**

```
后端 ──按 IF.md 实现──> 真实接口（网关可访问）
                          ▲
前端 ──按 IF.md 调用──────┘（联调时连真实后端）
```

- ❌ 错误做法：前端读后端 Controller 代码猜字段；后端读前端 API 封装猜需求
- ✅ 正确做法：**都以 IF.md 为准**，谁发现 IF.md 与实际不符，就改 IF.md（先确认再改）

### 8.5.2 职责边界（谁负责什么）

| 角色 | 职责 | 交付物 |
|------|------|--------|
| 后端 | 按 IF 实现接口，保证路径/字段/错误码/响应结构与 IF **一字不差** | 网关可访问的真实接口 + Knife4j 文档 |
| 前端 | 按 IF 的请求/响应结构写 API 封装与页面 | 页面 + `src/api/` 封装 + `src/types/` 类型 |
| IF.md | 唯一的接口契约，字段命名/类型/必填/错误码的裁判 | 文档（前端后端共同维护） |

### 8.5.3 联调时机与顺序

**后端先行，前端跟进，边做边联调**：

```
阶段 6（模型网关）后：后端每完成一个模块，前端就可并行联调该模块
                          ↓
前端开发对话：读 IF.md 该模块章节 → 写 API 封装 → 连真实后端验证
                          ↓
发现问题 → 记录到 PROGRESS「待解决」→ 判断是 IF 还是后端问题 → 修复
```

> 关键：**前端不要等后端全部做完才开始**，每个后端模块完成即可启动该模块的前端联调，缩短周期。

### 8.5.4 联调三步走（标准动作）

每次前端连后端，固定做三步：

1. **先通"健康"**：后端服务起没起、网关通不通（`curl` 或浏览器访问 `/health`）
2. **再通"单接口"**：先用 Knife4j 或 curl 验证后端接口返回是否符合 IF.md（字段、错误码）
3. **最后连"前端"**：前端页面真实调用，验证请求参数和响应渲染

> 顺序不能反。**后端接口没在 Knife4j 验证通过之前，不要开始前端联调**，否则问题会夹在"后端没对"和"前端没对"之间难定位。

### 8.5.5 字段命名与类型的硬约定（避免联调摩擦）

前后端最容易在字段上打架，定死以下规则：

| 项 | 约定 |
|----|------|
| 字段命名 | 严格按 IF.md，驼峰（`createdAt`），禁止前后端各自发挥 |
| 时间 | ISO-8601 字符串，前端只展示、不参与运算 |
| 金额 | 字符串（单位元，6 位小数），禁止用浮点 |
| 枚举/状态码 | 以 IF.md 的取值表为准，前后端各建一份枚举常量对齐 |
| 空值 | 约定：列表为空返回 `[]`，对象为空返回 `null`（在 IF 里明确） |
| 分页 | 统一 `pageNum/pageSize` + `records/total` 结构（见 IF §2.3） |
| 错误 | 统一 `code/message/traceId`，前端按 code 映射提示文案 |

### 8.5.6 联调问题归属判断（谁改谁）

出现"接口对不上"时，按下面规则判断：

| 现象 | 归属 | 处理 |
|------|------|------|
| 后端路径/字段/错误码和 IF 不一致 | **后端改** | 后端按 IF 修正 |
| 前端字段写错、类型不符 | **前端改** | 前端按 IF 修正 |
| IF.md 本身设计不合理/遗漏 | **改 IF** | 先你确认，再同步改 IF + 前后端 |
| 双方都对但语义歧义 | **改 IF** | 补充字段说明，消除歧义 |

> 口诀：**后端错改后端，前端错改前端，文档错改文档，别互相甩锅。**

### 8.5.7 前端联调对话的标准 Prompt

用「P8 前端联调对话」（见附录 B）。

### 8.5.8 联调完成的验收标准

一个模块联调完成，必须同时满足：

- [ ] 后端接口在 Knife4j 可访问，返回与 IF 一致
- [ ] 前端页面能真实调用后端，数据正确渲染
- [ ] 异常场景（错误码、空数据、加载态）前端有对应处理
- [ ] 流式接口（如有）SSE 能正常接收
- [ ] 联调结论已记录到 PROGRESS

1. 严格遵守 TD.md 的架构分层与设计约定，不写"能跑就行"的简化版。
2. 业务逻辑完整实现，不省略边界处理、不简化分支、不用 TODO/占位符搪塞。
3. 关键代码必须写清晰的中文注释（类/方法/关键分支/复杂逻辑），
   说明"为什么这么写"，而不是"做了什么"的废话注释。
4. 异常处理完整：不吞异常、不返回裸堆栈、错误码符合 IF 附录 A。
5. 入参校验完整（@Valid/JSR-303），不信任任何客户端输入。
6. 不写魔法数字/魔法字符串，统一提取为常量或枚举。
7. 命名规范、单一职责，方法不过长（一般 ≤ 50 行）。
8. 不生成伪代码、不生成空实现、不生成只返回 null 的占位方法。
```

## D5. 一次完整任务的标准对话长什么样（示例）

| ❌ 错误做法 | ✅ 正确做法 |
|------------|------------|
